**Fit dictionary shape (documented for W2–W5/P2; the brief pins the name, not the shape).**
`STANDARD_FIT` = `{&"engine": &"e_std", &"power": &"p_std", &"weapons": [&"w_laser"],

ShipFit.STANDARD_FIT)`.

## 4. Derivation of the acceptance arithmetic (W1 item 3)

`ship_vanguard` (Cutter): 08 §2 hull 1 000, shield 600, cargo 40, hardpoints 4,
power out 8, base speed 95 %. ENGINE_SPEC §13 handling: 428 u/s, 2.4 s, 2.0 s,
3.0 rad/s, 0.5 s. Fit: `e_std`, `p_std`, `w_laser`, `s_light`, `h_plate_light`.

1. Hull base (08 §2 + §13): 1000 · 600 · cargo 40 · 428 / 2.4 / 2.0 / 3.0 / 0.5;
   regen = 2/s (§4.2 base, no module yet); damage ×1.0; scan = lock = 900; tractor
   120 u / 90 u/s / 1 stream; `boosters` empty.
2. Flat: `h_plate_light` +250 hull → **1250**; `s_light` +200 shield → **800**.
3. Multiplicative, in 09 §5 order:
   armour speed `428 × (1 − 0.05)` = **406.6**; the same 5 % mass multiplies the
   handling times by `1 + |−0.05| = 1.05` → accel **2.52**, coast **2.1**,
   spin-up **0.525**; engine `e_std` ×1.00 → 406.6, turn ×1.00 → **3.0**; no
   computers → `damage_mult` **1.0**, scan **900**; regen `2 + 4` = **6.0**/s.
4. Clamps: 406.6 ≥ 0.4 × 428 = 171.2 ✓; hull 1250 ≤ 3 × 1000 ✓; shield 800 ≤ 3 × 600 ✓.
5. `lock_range` = `scan_range` = **900** (§4.1: the lock is the scanner's range;
   §13 pins 900 as the lock range).

## 6. Interpretation decisions (docs left these open; each has a reversal path)

1. **Base scan range = 900 (the one inferred number).** No doc states a bare scanner
   range; §13's combat table pins `rocket 900 (lock range 900)` and §4.1 makes lock
   range *be* the scanner's range, so `BASE_SCAN_RANGE` is 900 and
   `c_scanner`/`c_nexus` multiply it by 1 + 0.25. Reversal: change the one const.
2. **09 §3.3's "two heavy plates stack to −24 %" versus multiplicative stacking.**
   That same paragraph says the percentages are multiplicative, and §5 step 3 lists
   speed modifiers as multiplicative, so two `h_plate_heavy` give 0.88² = **−22.56 %**
   (not −24 %). Arithmetic follows §5; the −24 % prose is reported, not implemented.
3. **Plating subjects the handling *times*, not `turn_rate`.** §3.2 says plating
   "multiplies handling times by `1 + |its speed penalty|`"; `turn_rate` is a rate
   (rad/s), so it moves only with the engine (`e_vector` ×1.20). Reversal: divide
   `turn_rate` by the mass factor in `_apply_speed`.
4. **Pool clamp is per-pool.** "raise a pool above 3× hull base" is read as hull ≤ 3×
   hull base and shield ≤ 3× shield base (600 → 1800 for the Cutter), not both against
   the hull number.
5. **Regen = base + the best single module value** ("best value", §5 step 3; §3.2
   "the module regen above is added to that base"). Two `s_light` therefore give 6/s,
   not 10/s.
6. **The booster-on-activation speed modifier is not baked into the snapshot** (it
   depends on whether the booster is firing). `ShipStats.boosters` carries the fitted
   booster ids in fit order; the numbers are the module row
   (`ShipFit.MODULES[&"b_afterburner"][&"effects"]` = `boost_speed_mult 1.6`,
   `duration 3.0`, `cooldown 8.0`; `b_fold` = `blink_distance 400.0`, `cooldown 20.0`),
   so W2's afterburner has one source for its +60 %/3 s/8 s seam.
7. **`h_composite`'s "+10 % mass (boost weaker)" has no number in any doc.** It is
   carried as `mass_add 0.10` data on the module row and is *not* consumed by the
   resolver; what "weaker" means needs an owner number.
8. **Fields the pinned `ShipStats` has no home for are not invented.** Power output
   (09 §2) is reachable through the additive `power_budget()` instead of a new field;
   `u_drones` hull regen, `c_ewar`, `u_refine` and weapon damage/families resolve to no
   `ShipStats` effect (their consumers are slice 2/4).
9. **Fit legality is not modelled** (09 §4 items 1/3: mandatory pair, one module per
   typed slot, slot counts of 08 §3). The resolver trusts the fit; the clamp probe
   deliberately uses fits that are illegal by slot count to exercise the arithmetic.
   P2's fitting panel owns refusals; `power_budget()` is the arithmetic seam for it.
10. **Error behaviour:** unknown hull → `push_error` + `null` (the typed return is
    object-typed, so null is representable; asserted in the probe); unknown module id →
    exactly one `push_warning` per resolve and the id is ignored, so a fit referencing a
    not-yet-implemented module still resolves the rest.
11. **09 §3 names `game/module_catalog.gd` as the module table's home; slice 1's file
    list has no such file**, and the pinned interface makes `ship_fit.gd` the owner of
    the module effects. The table therefore lives in `ship_fit.gd` (`MODULES`); if P2
    wants the doc's split, moving the table is a pure move (the resolver reads it by id).
12. **Additions beyond the pinned minimum** (nothing renamed or removed):
    `ShipFit.fitted_ids()`, `ShipFit.power_budget()`, the three data tables and the
    constants of §3. `17_coder_handoff.md:37` already assigns power-budget validation to
    `game/ship_fit.gd`, which is why the budget arithmetic ships here rather than P2.
