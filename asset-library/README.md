# asset-library

**Search here first for any art.** This folder is the home of every generated asset and is not
part of the Godot project, so nothing here is imported by the engine and nothing here can ship
in an export or inflate `.godot/`. `vajb-orbit/assets/` holds only what has been pulled in.

## Read this before you use an asset

**The description is the truth; the file name is a hint.** Names in this library come from the
generation runs, and some of them lie outright: nine renders ignored the brief that produced
them and hold a spaceship where the name says "tileable layer" or "glow orb". Every one is
listed under `name_issue` in `_library.json` and at the end of `INDEX.md`. When a name and a
description disagree, the description was read off the pixels and the name was not.

Three ways to find what you need:

| Want | Use |
|---|---|
| A sentence about one file | `INDEX.md`, or `_library.json` -> `assets["cut/<name>.png"]` -> `description` |
| Something matching a need | search `_library.json` -> `assets[*].search_terms` |
| Something that ships | only rows whose `role` is `sprite`; `name_issue` must be null first |

`role` decides whether a file may be shipped at all:

- **`sprite`** (510) - one object, centred, cut out of a sheet. This is what a feature loads.
- **`plate`** (30) - a whole-frame layer: backdrop, tiling layer, menu or loading screen. No
  object and no background to key, so it is used as-is and never keyed.
- **`sheet`** (163) and **`sheet-keyed`** (7) - the raw renders, kept as provenance. Never ship
  one; they are the source the cutter reads.
- **`needs_keying`** is true for 484 sprites: they are RGB with the render backdrop still in
  them. Keying is the next pass, and it reads `cut/`.

## Archived (2026-09-21)

Every sprite the game needs is inside `vajb-orbit/assets/`, so the source trees — 1.26 GB of PNG
nothing reads at runtime — are zips in `_archive/`:

| Archive | Holds |
|---|---|
| `raw_2026-09-21.zip` | the 172 raw renders: 150 sheets, 7 keyed references, the run manifests |
| `cut_2026-09-21.zip` | the 488 shippable cuts: 445 sprites and 43 plates, one file per asset |
| `dropped_2026-09-21.zip` | the 74 ruled-out renders from the naming pass |

Each zip passed two checks before its loose copy went: `zipfile.testzip` over every entry, and
twelve md5 comparisons between the archive bytes and the files on disk. `staging/cut/archive.py`
puts any tree back in place:

```
py -3.14 staging/cut/archive.py --state                  # what is loose, what is archived
py -3.14 staging/cut/archive.py --restore cut            # unzip one tree
py -3.14 staging/cut/archive.py --make cut --prune cut   # re-archive after a change
```

**Restore `cut/` before running anything that reads it** — `pull.py`, `key_flat.py`,
`center_check.py` and `validate_names.py --library`. `build_library.py` refuses to run against
an emptied tree rather than overwrite the index with nothing (`--allow-archived` overrides).
`_library.json` and `INDEX.md` were built while the tree was loose and remain its record.
`_prekey_backup/` and `_keying/` stay loose on purpose: they are the keying pass's reversibility
store and the paid answer cache that keeps a re-key from re-billing.

## Naming is done

**Every file has a name the specs and the code agree on.** `staging/cut/validate_names.py
--library` is the check, and it reports that every name the specs and the code require is
present: all 16 panel masters, all 23 sanctioned glyphs, 20 minerals, 20 ingots, 8 slots,
5 contracts, 3 services.

The tree mirrors `docs/design/ASSET_NAMING_SPEC.md` section 3:

```
cut/ships  cut/icons/{mineral,ingot,cargo,contract,map,booster,equip,module,weapon,
                       insignia,service,slot,status,hud,alt}
cut/env/{backdrop,tile,body,pickup,poi,prop}   cut/fx   cut/ui      (raw/ mirrors it)
```

| Where | What |
|---|---|
| The law | `docs/design/ASSET_NAMING_SPEC.md` |
| The decisions, per file with their evidence | `staging/cut/_naming/assignments.tsv` |
| Why a name was chosen | the `evidence` and `note` columns: `icons-spec-8`, `shipped-manifest`, `matches-0.963`, `render`, `owner` |
| Undo | `_rename_map.json` holds all 732 moves; `apply_names.py --undo` reverses them |
| What was dropped and why | `_dropped/` plus the `drop` rows in the table |

72 files sit in `_dropped/`: second renders of art that already has a name, and eight renders
that defied their own brief and produced a spaceship where the prompt promised a layer or an
effect. They are kept so the ruling stays inspectable.

## Keying is done

Every sprite in `cut/` is RGBA. **441 sprites needed the backdrop gone; all 441 have it gone**,
each centred on its canvas within 1 px (`_keying/center_report.json`). The route per file:

| Route | Files | What it is |
|---|---|---|
| `recraft/remove-background` (kie.ai, 1 credit each) | 407 | ships, env, ui and every icon whose object is painted or whose backdrop is a soft vignette |
| Python, flat-field regions (`staging/cut/key_flat.py`) | 34 | the flat icons: a single-colour figure on a flat field, where the paid matte read the figure as background and the field as the object |

The 34 are listed in `staging/cut/_flat_icon_applied.txt`; the comparison that chose them is
`_review/flat_icons_check_*.jpg` (original | python | recraft, 35 files, and
`icon_module_b_fold` kept recraft because it is the one render that really is a white figure on
a dark card). `staging/cut/_bright_ink.txt` is how they were found: their recraft matte was
mostly near-white ink, which for an iron-black silhouette means the matte is inverted.

Records, all under `_keying/`:

| File | What it holds |
|---|---|
| `recraft/<name>.json` + `-recraft.png` | per sprite: upload url, job id, the payload field that was accepted (`image`; `image_url` answers "image is required"), and the raw answer, keyed by the md5 of the pre-key file so a re-run never re-bills |
| `recraft_ledger.jsonl` | one line per paid call: 441 credits total ≈ $2.21 at the console rate (10 credits = $0.05) |
| `recraft_failures.json` | written only when a batch leaves failures; absent means none |
| `center_report.json`, `center_shifts.json` | the measured offset per sprite, and the 222 shifts applied to centre them |
| `flat/`, `ab/` | the Python candidates and the A/B evidence for the flat-icon decision |
| `../_prekey_backup/` + `manifest.json` | every pre-key RGB file, md5-stamped; `key_assets.py --undo` restores them |

Two failure modes were found and are worth knowing before trusting any single route:

- **The paid matte inverts a flat render.** On `icon_zoom_plus` (an iron-black magnifier on
  white) recraft kept the white field and cut the magnifier out. It is right for painted
  subjects and wrong for clean flat silhouettes; the flat-field Python key is right for those.
- **The Python key keeps a dark card.** On `icon_module_b_fold` (a white arrow on a dark card)
  every flat field is the background, so the arrow survives under recraft and the card survives
  under Python. The guard in `key_flat.py` refuses a result that still covers most of the
  canvas, which is how such renders stay on recraft.

QC: `_review/key_check_final_p*.jpg` (18 pages, every keyed sprite on checkerboard) is the
record to read; `key_assets.py --qc` rebuilds it. Centring is measured, never assumed:
`staging/cut/center_check.py --report` prints the offset table, `--apply` shifts, and every
shift is verified by re-measuring and rolled back if the offset grew.

## The pipeline

```
raw/ --(build_plan.py)-----> _sheets.json ---------\
     \--(deepseek_layout.py)-> _layout_deepseek.json -+-> cut_sheets.py -> cut/
                                                        |
cut/ + raw/ --(tag_vision.py)--> _vision.json ----------+
docs/ + vajb-orbit/ --(vocabulary.py)--> _vocabulary.json
                            \--> build_library.py --> _library.json + INDEX.md
```

```
py -3.14 staging/cut/build_plan.py             # re-derive the plan from the manifests
py -3.14 staging/cut/deepseek_layout.py        # ask a vision model for each sheet's arrangement
py -3.14 staging/cut/cut_sheets.py --replace   # cut every sheet (--check reports only, --only narrows)
py -3.14 staging/cut/build_review.py           # refresh the cut contact sheets
py -3.14 staging/cut/tag_vision.py             # describe every file (resumes; --report shows progress)
py -3.14 staging/cut/vocabulary.py             # collect the names the docs and the code already use
py -3.14 staging/cut/build_library.py          # write _library.json and INDEX.md
py -3.14 staging/cut/peek.py --all-suspicious  # tile sheet, to check a description against its picture
py -3.14 staging/cut/find_matches.py           # which named sprite each unnamed sprite duplicates
py -3.14 staging/cut/build_naming_digest.py    # the naming pass's working set, as small flat files
py -3.14 staging/cut/naming_assignments.py     # the naming decisions, as data
py -3.14 staging/cut/validate_names.py         # check the plan against the naming law
py -3.14 staging/cut/key_assets.py --recraft --scope local   # key via kie.ai (resumable, 20/min)
py -3.14 staging/cut/key_assets.py --qc --scope all          # contact pages of the keyed sprites
py -3.14 staging/cut/key_flat.py --check <name>...           # flat-field Python key (flat icons)
py -3.14 staging/cut/center_check.py --report                # how far off centre each object is
py -3.14 staging/cut/center_check.py --apply                 # centre them, verified per file
py -3.14 staging/cut/pull.py --check           # what would move into the Godot project
```

The rename chain, in order: `find_matches.py` measures which unnamed sprite duplicates which
named one, `build_naming_digest.py` writes the working set a naming pass reads,
`naming_assignments.py` records the decision per file with its evidence, `validate_names.py`
checks the plan against `docs/design/ASSET_NAMING_SPEC.md`, and only then does a rename run.

`cut_sheets.py` never deletes, so it refuses to run into a folder that already holds files until
`--replace` says the old ones are expendable: names change between runs, and a silent mix of two
runs is worse than an error.

### How a sheet becomes sprites

1. **Layout.** How many panels a sheet holds, and their order, comes from the recovered Phase
   D/E/F specs and the prompts. Which way round those panels lie (3 columns x 2 rows or 2 x 3)
   is read from the render by `deepseek_layout.py`, because the prompts are ambiguous about it
   and some renders ignored the request, and a wrong guess mis-names every icon on the sheet.
2. **Objects.** The cutter masks the ink, bridges the gaps inside one shape, drops the film
   grain, and gathers every piece whose centre falls in a cell. So a pylon and its beacon, or a
   glyph drawn in several strokes, come back as one sprite, and no divider a few pixels off can
   slice an object.
3. **Canvas.** Every sprite of a sheet is the same size and the object sits dead centre. The
   `icons` family additionally shares one 512px square canvas with each icon scaled to one share
   of it, so the whole icon set is one size and one visual weight. Other families keep their own
   scale: a ship must not change size as it turns through its four views, and an S asteroid must
   stay smaller than an L one.
4. **Plates.** Sheets that are whole-frame layers rather than objects are copied through
   untouched. `_sheets.json` records which, and why.
5. **Keying.** `cut/` ships RGBA: the backdrop is keyed by `key_assets.py` (401 files in the
   recraft batch, 92 of them ships) or `key_flat.py` (the 34 flat icons), then every object is
   centred by `center_check.py`. What each file got, and the evidence, is in the section above.

### How a description is written, and why it can be trusted

`tag_vision.py` sends each file to `deepseek-chat` scaled to 768px (2048 for a sheet, which holds
many panels) and asks what is in it. A cut sprite is asked for its subject, kind and a
distinguishing detail; a raw sheet is asked for every object it can see, in reading order, which
means one call names every panel cut off that sheet.

The model choice is measured, not assumed. Same sprite, prompt-token count with and without the
attachment, which is what proves an image was read:

| Model | Route | Delta | Output | Verdict |
|---|---|---|---|---|
| `deepseek-chat` | api.deepseek.com | +206 | 5 | sees it, answers at once |
| `deepseek-flash` | api.deepseek.com | +206 | 12288 | sees it, reasons at length |
| `deepseek-v4-flash` | api.deepseek.com | +206 | 300, empty | sees it, truncates at a normal budget |
| `deepseek-v4-pro` | api.deepseek.com | +5 | 224 | drops it: "Cannot identify without the image" |
| `deepseek-v4-flash-vision-exp` | opencode-go | +206 | up to 4096, empty 2 of 8 | sees it, stalls |
| `deepseek-v4-flash` | opencode-go | - | - | HTTP 400, text only |

The whole 710-file pass cost about **$0.13** (401k prompt, 39k completion) and answered every
file. Descriptions are spot-checked against the pixels with `peek.py`; that is how the nine
`content-mismatch` files were found, and no file is added to that list without a look.

## Not done yet

1. **Names.** 188 files still carry a placeholder name (`<family>_sheet_NxM_<stamp>[__pNN]`),
   19 carry a `__<stamp>` twin that collides with a live name, 32 carry the generator's own
   filename, and 5 carry a phase prefix. All 244 are listed in `_library.json`.
2. **Pull state.** Whatever the last `pull.py` run moved into `vajb-orbit/assets/`; the manifest
   row per family records it, and `pull.py --check` says what would move now.
3. **Derived sets.** The icon quartets (`_16/_48/_96/_192`), `icons/tint/` and the chrome `@2x`
   cuts are not built here; they are derived from the icon masters after those land in the
   project.
4. **The rest of the inverted renders.** The flat-icon pass covered the 42 sprites whose recraft
   matte read as mostly near-white ink. If a later look finds more (the check is cheap: run the
   bright-ink audit in this README's Keying section over `_library.json`), `key_flat.py --check`
   prints the candidate before anything is written.

## The alpha history, in one paragraph

The v1 matte (`staging/phase_d/reprocess.py`, now deleted) keyed every pixel within a distance
of 16 of the estimated background. Measured against the raw renders, **51-76% of the area it
keyed out was rendered artwork, not background** - a hull's shadowed plating sits inside that
distance - so it punched blotches through every ship, prop and icon. Its output was thrown away
and the pipeline rebuilt from `raw/`. Contract: `docs/design/ASSET_PIPELINE_V2.md`.

The v2 answer, executed 2026-09-20, is in the section above: a paid matte
(`recraft/remove-background`, 1 credit per sprite) where the backdrop is soft or the subject is
painted, a region-based flat-field key where the render is a clean figure on a flat field, and a
measured centring pass over both. Everything is cached, backed up, and reversible.
